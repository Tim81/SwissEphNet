## Area provenance

Every regeneration (reference or local) replaces the *entire* set of
baseline-*.tsv files -- scripts/regenerate-baseline.ps1 has no per-area or
per-row logic (see its own comments). What actually distinguishes a
"package-2.8.0.2" area from a "local-<sha>" one below is not which script
invocation last touched the file on disk, it is whether the file's current
*content* is still byte-identical to what that original 2.8.0.2 package run
produced, verified area by area, not assumed:

- `package-2.8.0.2` means: this area's committed content is confirmed
  byte-identical to the original reference-mode run recorded in the eight
  fields at the top of this file. It proves "unchanged since 2.08" -- an
  actual oracle, because the reference package predates any local code this
  repo might have since patched.
- `local-<short-sha>` means: this area's committed content was last produced
  by `-FromLocal` at the given commit (see "Local regenerations" below for
  what changed and why). It proves only "unchanged since the day it was
  written" -- a regression net against future drift, not an oracle against
  2.08, because local code authored the content in the first place.
- `mixed` means: most of the area is still package-seeded, but a named subset
  of rows has been re-seeded locally. Read the two guarantees above as applying
  row by row: the named subset carries the weaker one. An area lands here when
  a deliberate fix changes some of its rows without touching the rest, which is
  the normal shape of a fidelity fix. Do not collapse it back to
  `package-2.8.0.2` on the grounds that "most of it" still is, and do not
  collapse it to `local-` either: the first overstates the guarantee for the
  re-seeded rows, the second understates it for every other row and would
  discard a real oracle.

  A subset that has been independently validated against upstream C is worth
  saying so about, because it is a stronger claim than either label. The 375
  `HP|G|*` rows re-seeded in PR #13 were checked against Astrodienst's own
  2.10.03 libswe (via the `pyswisseph` 2.10.3.2 wheel, which bundles it) and
  are bit-exact, not merely within tolerance. That is not the same as
  package-seeded provenance and does not restore it, but it does mean those
  rows are known-correct rather than merely frozen.

## pyswisseph 2.10.03 validation coverage

The eleven `local`/`mixed` areas above prove "unchanged since the day they were
written" -- a regression net, not an oracle against 2.08. `scripts/validate-seeded-
areas.py` closes part of that gap: it replays each area's rows through `pyswisseph`
2.10.3.2, which bundles Astrodienst's own libswe **2.10.03** (the version
`external/swisseph` is pinned to), and classifies each row as agreeing, disagreeing,
or not reconstructible via that binding.

**Read this as a different, narrower claim than `package-2.8.0.2`, not a stronger
one.** `package-2.8.0.2` proves byte-identity with a real 2.08 assembly run --
an oracle for what 2.08 actually did. This proves agreement (or not) with real
**2.10.03** C, a version two minor releases ahead of the port. A disagreement
here does not mean the port is wrong: it may be a deliberate 2.08 behaviour
2.10.03 later changed. Two such changes were traced to a specific commented-out
line in the vendored 2.10.03 source and are recorded below; most disagreements
were not traced that far and are reported as magnitude/pattern only. Agreement
here is the stronger signal: bit-exact or within-tolerance agreement with real
2.10.03 C, for the specific inputs each row exercises.

`astromodels` is out of scope for this method entirely: pyswisseph exposes the
`MOD_*`/`MODEL_*` constants but binds none of `set_astro_models`,
`get_astro_models`, `set_interpolate_nut` (confirmed against its 101 callables),
so there is no pyswisseph call this area's rows can be replayed against.

The replay always points pyswisseph at a freshly created **empty** ephemeris
